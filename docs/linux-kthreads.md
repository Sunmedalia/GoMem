# Linux kernel thread entry functions (development preview)

`linux.kthreads` implements native kernel-thread entry inspection for symbol-described Intel Linux kernels with `kthread.threadfn` (Linux 5.8+). It provides the pinned Volatility 3 v2.28.2 Kthreads columns TID, Thread Name, Handler Address, Module and Symbol, plus evidence and coverage records. This remains a **partial** capability with synthetic positive coverage and an old-kernel applicability test; no modern real-image acceptance is established.

```sh
bin/gomem analyze linux.kthreads --image memory.raw --symbols kernel.json --offline --case case-001 --format jsonl
```

Task-list leaders and their threads are inspected in traversal order, excluding `init_task`. Both the legacy `thread_group` and modern `signal_struct.thread_head/thread_node` lists are supported. PF_KTHREAD (`0x00200000`) selects kernel tasks. The private kthread pointer comes from `worker_private` when that field exists, otherwise `set_child_tid`. A readable nonzero private target and nonzero readable `threadfn` target are required. Native private/handler readability probes capture one byte and do not infer executable permissions. The fixed Pointer.is_readable uses the declared target subtype extent; complete equivalence for other subtype sizes remains pending. Names start with `task.comm`; an available, readable `kthread.full_name` replaces it using a 255-byte read, including an intentionally empty name. An unreadable name byte range retains the read proof and comm fallback. A failed required name-pointer field read remains a task failure.

The plugin reuses [module cross-view discovery](linux-modxview.md) for Lsmod, SysFs and Scanner and adds the `__kernel__` code range from `_text` to `_etext`. The kernel range is symbol-derived, retaining its symbol digest rather than pretending the bound is a memory read. First-seen masked module bases win across gatherers. Pointer lookups use the first matching half-open range; all matches and overlaps remain evidence. Full canonical object/handler addresses remain in native evidence. Matching uses the current Intel layer's 48-bit x64 or 32-bit x86/PAE mask.

Kernel symbols match exact addresses, taking the first lexicographic alias, using an index built once per run. Module symbols use legacy module `symtab/strtab/num_symtab`, or pointer/embedded `kallsyms`, reading standard ELF32/ELF64 entries with the declared byte order. The first nonempty name at the exact address wins. The pinned helper's inclusive iteration limit is preserved: indexes 0..4096, at most **4,097** entries. Declared entry counts, the search limit and whether the whole table fits remain in `module_symbol_window`. Names have a 512-byte capture bound. Interior instruction addresses do not receive a guessed nearest symbol. Qualified symbols keep the component immediately after the first `!`, as the fixed helper does.

There is an explicit reference difference in non-kernel symbol ownership. The fixed `Modules.module_lookup_by_address` selects `match = matches[0]`, but then constructs the module object using the final loop variable's `module.offset`. This can resolve a symbol against a different object. GoMem resolves symbols against the **selected matching module**. `symbol_owner_policy` records the selected object, the pinned final-range object and whether those owners differ. The fixed-source oracle preserves the unmodified lookup/generator output and separately invokes the unmodified symbol helper on the selected object. For example, the synthetic thread at handler `0x10100` maps to active module `0xc000`: GoMem resolves `module_entry`; the pinned generator's final kernel-range object has no such symbol. This explained difference prevents a complete-parity claim.

`kthread` rows contain selected handlers. `task_observation` rows retain user-task and skipped-pointer decisions. Module source/candidate/selection records remain in the output, followed by a coverage summary. Raw evidence includes task flags, identifiers, available scalar creation counters, list links, private/handler pointers and target probes, names, ELF entries and string bytes. The task identity combines image, layer, object address, TID and available creation time. Kernel/module addresses use lossless hexadecimal values. Missing modules/symbols remain explicitly unavailable.

Null pointers are recorded skips. Unreadable required private/handler targets, field/layout failures, damaged lists, missing module sources and bound exhaustion retain partial observations and fail the task. This is stricter than the fixed plugin's silent pointer skips and padded ELF name reads. Native symbol names require the complete 512-byte capture; partial bytes remain evidence and are not padded into a claimed name. Cancellation and output errors return immediately. Strict forward backlink/tail checks do not reproduce every fixed task validity check, bidirectional recovery or duplicate-thread behavior.

Defaults are `max-nodes=131072` (1..1,000,000 source visits and per-list bound), `max-tasks=1000000` (1..1,000,000 inspected tasks/threads) and `max-scan-bytes=268435456` (1..8 GiB allocation span). Module captures retain the shared 4,096-byte field/struct bound. These are explicit native limits; missing reads never become a successful empty result.

Validation includes 39 combinations of x64/x86/PAE paging and 13 positive/skip/fallback layouts, plus unreadable pointers/symbols, damaged thread links, missing/inverted kernel bounds, unsupported kthread types, bounds, cancellation and output failures. Positive fixture runs emit 22 records each and independently reread all complete raw captures (84..104 per profile). Selected rows match the fixed generator for TID/name/handler/module; symbols match the fixed symbol helper on the selected owner, with the reference ownership difference above retained. All persisted rows verify, completed tasks reuse their cache, and a synthetic evidence bundle verifies. Timestamped report manifests are excluded when checking repeated exported evidence bytes.

The user's Debian 3.2 RAW image is rejected by both the unmodified fixed plugin (confirmed in its verbose traceback) and the native applicability check before producing entity rows; repeated execution persists failed tasks and does not reuse successful cache state. This is **not** a positive real-image differential. The user's Kali ARM64 LiME image still needs an ARM64 virtual translator and actual kernel symbols. A successful physical VMCOREINFO scan does not establish kernel-thread support.
