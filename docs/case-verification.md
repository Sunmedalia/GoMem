# 案件完整性验证（v0.1）

```sh
gomem case verify --case ./case-001
gomem case verify --case ./case-001 --task <task-id>
```

命令在现有案件的独占锁内运行，逐页读取结果（每页 500 行），不打开原始镜像。不存在的案件、空案件和不存在的 task 都明确失败，不会创建空案件再返回成功。使用标准案件打开流程，之前中断且未终结的任务会按照现有恢复规则标记为 failed，保留其部分证据。

验证内容：SQLite quick_check 与外键、结果索引 ID 与正文 ID、一行一摘要的 Seal、任务的完成元数据、源镜像/引擎/符号/参数归属、同任务先前输出的父节点、references 类型的目标存在/Seal/镜像一致性，以及案件中的全部提取文件与空洞日志校验。

分诊 finding 继承来源插件的符号和参数，并使用 `triage.<rule>` 归属。因此其任务归属核对镜像与引擎身份，并核对原始引用，保留源参数而不强行改写成分诊参数。

输出包括 `verified`、任务/行/引用/提取文件计数、`task_states`。failed/canceled 任务的合法部分证据可以通过存储验证，原任务状态原样显示；它们不会因此升级为 completed。发生损坏时输出 `verified=false` 和已经核对的计数，同时返回非零退出码。

这是存储一致性验证，不是镜像正常判断、完整分析覆盖或数字签名认证。没有独立外部清单时，不能证明所有历史行都未被删除，也不能阻止攻击者同时重写数据和摘要。`--task` 只完整检查所选任务及其直接引用；SQLite 结构和外键仍作全库检查，提取文件验证以所选任务为范围。搜索索引和人工笔记不在此版本验证范围中。

测试包括跨三页的 1,001 行、读取取消、缺失任务、正文和索引篡改、重算摘要后的跨任务身份错配、悬空父节点、悬空引用、终结元数据损坏、孤立外键、分诊来源保留及提取文件篡改，并覆盖 CLI 分析/缓存/导出/分诊后的案件验证。

2026-10-23 本地验证：存储、CLI、报告三个包的完整竞态测试通过。已有 Debian PIDHash 案件的 6,815 行通过检查；使用用户提供的 `images/kali.raw` 新跑物理 VMCOREINFO 得到 115 行（包含诊断/覆盖记录，不能等同于 115 个键），新案件的全部行通过检查。这两次案件验证均不打开或重写源镜像；这次 Kali 案件检查使用的是物理元数据结果。
